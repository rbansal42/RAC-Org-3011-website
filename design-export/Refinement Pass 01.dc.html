Where the brief and the repository part company

Four points, in the order they matter. The first two are now settled decisions and are recorded here so the next person doesn't relitigate them; the last two are live mismatches that still need resolving.

Tailwind doesn't exist yet — it's the target, not the source.

The site today is Vite + React styled with inline style objects and one 1,015-line src/index.css; there's no tailwind.config and Tailwind isn't in package.json. Since Tailwind is now the plan, the first job is porting the :root custom properties out of that stylesheet into theme.extend rather than authoring a fresh scale — the values below are the ones to carry over verbatim. Do this before any page work: adding Tailwind alongside 1,015 lines of live CSS and several hundred inline style objects means three styling systems competing, and whichever lands last wins by accident.

The palette is the current site's, not maroon on cream.

Settled: the live values stand. #D81B60 is a magenta-pink, not a burgundy, and it sits on #FFFFFF with #FDF8FA as the subtle ground — a pink-tinted near-white rather than a cream. --rotaract-cranberry-dark #880E4F is declared but barely used, and it's the one worth putting to work: it's the only value in the file with enough contrast for accent-coloured body text, which #D81B60 doesn't have at paragraph sizes.

This document is set in that palette, so it doubles as the reference.

The gold layer is contradictory, not merely unused.

--skyline-gold, --skyline-gold-light and --skyline-gold-dark are all set to the same value, #123499 — a navy blue. Meanwhile .btn-gold and .pill-gold still carry gold rgba(197,160,89) shadows. So a blue button glows gold. "Reuse the existing tokens" inherits this; it needs resolving before anything else consumes those three variables.

Showcase is not an existing page.

There's no router — App.jsx hand-rolls a ROUTE_MAP of eight paths over pushState, with no 404 branch, so any unknown URL silently renders home. /showcase is not among them. The closest existing thing is ClubInitiativesList.jsx, nested inside /directory. Section 3 below is therefore a specification, not a before/after.

1. Home

The sluggishness is not diffuse. It is four rules in index.css, lines 301–338.

The cause

scroll-snap-stop: always on every full-height section forbids skipping. A visitor physically cannot flick down the page; each section is a mandatory stop. That is the scroll-jacking — it isn't JavaScript hijacking the wheel, it's CSS refusing to let go of it.

scroll-behavior: smooth on the same container animates every one of those forced stops, so a single wheel tick buys a full transition before the next input is honoured.

height, min-height and max-height all pinned to 100vh with overflow: hidden means anything that doesn't fit is clipped rather than scrolled, and the whole page re-lays-out every time mobile browser chrome shows or hides.

Layered on top, the hero runs five animations simultaneously:

  • ScrambleTitle — a 45ms setInterval doing a full split/map/join across the string on every tick, randomising letters until it settles.
  • TypewriterText — a second interval, one character at a time.
  • InteractiveDotGrid — a canvas particle field spelling out "Fellowships through service".
  • BigRotaryWheel — scroll-position-driven transforms, with its own rAF loop.
  • The sectionFadeUp keyframe on every section entry.

Plus the custom two-part cursor in App.jsx, which on every mousemove runs e.target.closest('[data-cursor]') — an ancestor walk per pointer event — and then calls setState. And before any of it: a fixed 2.2-second pink curtain on first load, followed by a second full-screen glass spinner on each tab change.

After

ChangeWhat it buys
Delete the whole snap layer — .snap-container, .snap-section, .snap-section-footer and the mobile !important overrides that undo themSections become ordinary blocks with min-height and real padding. Scroll becomes free. This alone is most of the fix.

2. Map

The heaviest page, and the causes are specific rather than inherent to maps.

Two raster tile layers load on every visit.

Esri World_Imagery satellite, then a Carto voyager_only_labels overlay at opacity: 0.9 on top of it. Satellite is the heaviest basemap available and it's the default, so every visitor pays for imagery before anyone has asked to see it — doubled, because the labels come as a second full tile set.

Every marker is destroyed and rebuilt on every keystroke.

renderLeafletMarkers opens by removing all markers, then re-creates the filtered set — and it's wired to an effect keyed on activeClubs, searchQuery and activeZoneId with no debounce. Typing four letters into search tears down and re-creates the full pin set four times, each pin a divIcon carrying the .leaflet-neon-marker glow, whose layered box-shadows then repaint as the map moves.

Zone filtering sniffs strings.

Each zone is matched by a hand-written list of substring aliases — includes('prithvi') || includes('south'), and so on for four zones. A club whose zone field is spelled any other way silently disappears from the map instead of failing loudly.

Club records are joined by fuzzy name match, twice.

The Excel roster is matched to club records by stripping rotaract, club, of and whitespace, then testing substring containment in both directions. Any club name that is a prefix of a longer one will collide, so presidents, phone numbers and blood groups can attach to the wrong club — quietly. The same routine is duplicated in App.jsx and DistrictMap.jsx, so the two can disagree. This is the schema concern from the planning call showing up as a rendering bug.

After

ChangeWhat it buys
Default to the light Carto basemap alone; satellite becomes a toggle that adds the Esri layer on demandOne tile set at rest instead of two, and the light one. Satellite stays available for the people who actually want it.
Hold a marker map keyed by club id; on filter change add and remove only the delta. Debounce search at 200msTyping stops rebuilding the map. Pins that stay visible never re-mount, so their glow never re-rasterises.

States this page needs designed, not just a happy path

Loading. Reserve the map's box with aspect-ratio and paint a flat skeleton inside it — the district outline in --border-light, pins as plain dots at their real positions. Layout is final before a single tile arrives, so there is no shift, and the shape of the answer is visible immediately.

Tile failure. If the layer errors, keep the pins and swap the map for the club list. The page's value is the clubs and their contacts, not the imagery — it should degrade to a directory, not to an empty grey box.

Empty filter. Keep the map framed on the selected zone, name the zone, say it has no clubs listed yet, and offer a single clear-filter action. Never an empty map with no explanation.

3. Showcase

What exists today is ClubInitiativesList.jsx inside /directory: a search field, a zone dropdown, and a list of clubs with their initiatives nested underneath. Four things about it shouldn't carry forward.

  • It's keyed by club, not by project. To see any work you must first decide which club to look at — the opposite of a showcase, which should let the work argue for itself.
  • The section's subtitle spends fifteen words on process: "Manually curated flagship community service initiatives selected by Club Presidents & District Officers." Nobody arrives wanting to know the curation method.
  • Filters are search and zone only. The brief needs club, zone and category/avenue.
  • "+ Add Featured Initiative" renders unconditionally, so every public visitor sees a button they can't use.

Specification

Card

A 4:3 image with the box reserved by aspect-ratio and loading="lazy" decoding="async"; then club name, date, one category tag, and the summary clamped to four lines with -webkit-line-clamp. Fix the text block's height so a three-line summary and a one-line summary produce the same card — a ragged grid reads as broken data.

Grid — not masonry

grid-template-columns: repeat(auto-fill, minmax(300px, 1fr)). Masonry either needs grid-template-rows: masonry, which isn't broadly shipped, or JavaScript measurement that re-flows on every filter change — precisely the pattern causing the complaints elsewhere. With a fixed card height there's nothing for masonry to do anyway.

Filter bar

Three selects — club, zone, category — plus a clear-all that only appears once something is set. Filter in memory against data already fetched, and toggle visibility on the existing nodes rather than remounting the grid, so filtering never re-requests an image that was already on screen.

Loading, empty, detail

Loading. Eight skeleton cards at the card's exact dimensions, so the grid never reflows when real data lands.

No matches. State the filters currently applied and offer clear-all. A bare "no results" makes the user guess which of three filters is the culprit.

A club with no projects yet. This is where the tagline actually earns its place rather than being decoration: "It all starts with Rotaract and everything good happens." followed by the plain fact that this club hasn't added a project, and — for a signed-in president only — the link to add one.

Detail page. /showcase/[project-id]: photos, the full write-up, club attribution linking through to that club's leadership page, and three related projects by category. Without this route the four-line summary is the entire story, which wastes the submissions you already have.

Three things I need from you

  1. Every flagship project on the homepage currently pairs an Unsplash stock photo with a specific claim — 12,500+ units, 66,000 saplings, 20,000+ children screened. Stock imagery under precise numbers is the site's biggest credibility problem and no amount of refinement touches it. Are real event photographs available?
  2. Club-submitted showcase projects sit behind a P1 approval gate that the call flagged as risky. Should the showcase be designed assuming submissions exist at launch, or seed-only from the July–August MDIO form data?
  3. The four project sections ship as separate deployments but must share header, footer and component library. With no shared package today that means either copying the components into four repos, where they will drift within weeks, or extracting one shared package first. Which?
